# Truth table for the cross-engine comparison.
#
# ROLE: a label set plus a human-readable frequency column. It is NOT a third
# independent check on `noteHz` and must not be read as one.
#
# Both emitters gate on `xcells.json`'s own `noteHz`:
#   - CrossEngineComparisonTests.swift  -> cell.noteHz
#   - xeng.mjs                          -> cell.noteHz from the manifest
# and xcompare.py scores the `first`/`last` values those two already produced.
# Nothing here re-derives a verdict from this file, so a disagreement between
# this column and the manifest would not change any number in the table.
#
# What it IS used for, and is load-bearing:
#   1. The third leg of the label-parity check. xcompare.py refuses to score
#      unless the labels here, in the StrumKit trace and in the WebTuna trace
#      are the same set. That catches a cell silently vanishing from either
#      side, which the two traces alone cannot detect.
#   2. The `truth` column printed in the table, so a reader does not have to
#      open the JSON to check a number.
#
# GENERATED FILE - regenerate, never hand-edit. This file is exactly
# `xtruth-header.txt` followed by one `label=noteHz` line per manifest entry.
# The recipe in ../README.md rebuilds it from those two committed inputs and
# never reads its own output, so running it is idempotent and it works even
# when this file has been deleted. A hand-edited value here would be silently
# reverted by the next regeneration, and until then would not be what the
# generator produces - which is exactly how three `110.0`/`440.0` lines got in
# once.
